**Step 6 — Cloudinary (asset persistence)** (`src/lib/cloudinary.ts`, `src/app/api/generate/[taskId]/route.ts`, `scripts/backfill-cloudinary.mjs`)
- **Credentials verified live before building anything**: `CLOUDINARY_CLOUD_NAME`/`CLOUDINARY_API_KEY`/`CLOUDINARY_API_SECRET` were already in `.env` (user-provided) — confirmed working with a real `cloudinary.api.ping()` call before writing the integration, not assumed. `cloudinary` npm package (v2 SDK) installed.
- **Part 1 — re-upload on completion**: `src/lib/cloudinary.ts`'s `persistVideo(sourceUrl, publicId)` uses Cloudinary's upload-by-remote-URL (`cloudinary.uploader.upload(url, { resource_type: "video", ... })`) — Cloudinary fetches the BytePlus URL server-side and stores its own permanent copy, functionally equivalent to a manual download+reupload without proxying the video bytes through this app's own server. Same retry-once-then-null contract as `byteplus.ts`/`agent.ts`. Wired into `GET /api/generate/[taskId]`: the moment BytePlus reports `status: "succeeded"`, this route uploads to Cloudinary and only ever returns the permanent `res.cloudinary.com` URL as `videoUrl` — the raw BytePlus URL never reaches the frontend or gets written to `generation_tasks.media_url`. If the Cloudinary upload fails after its retry, the route returns `status: "error"` with a friendly message instead of silently leaving the temporary BytePlus URL in place — the existing `VideoNode` Retry button (built earlier this session) handles recovery, no new UI needed.
- **Part 2 — backfill script** (`scripts/backfill-cloudinary.mjs`, run via `npm run backfill:cloudinary`, i.e. `node --env-file=.env scripts/backfill-cloudinary.mjs`): a plain Node ESM script (no `tsx`/`ts-node` needed, no queue/job infra per ponytail-mode instruction) using the Supabase **service role key** (bypasses RLS — this is an admin migration across all users' rows, not a per-user request) to find every `generation_tasks` row where `type` is `video`/`image`, `status = 'completed'`, and `media_url` doesn't already contain `cloudinary` (domain-agnostic to exactly which BytePlus CDN host issued the original URL). For each: re-uploads to Cloudinary and updates `media_url`; on failure, logs the task id + reason and sets `status: 'error'` so it's visibly marked dead in the UI (reuses the existing Failed+Retry treatment) rather than silently leaving a broken link. Prints a final summary (checked/migrated/failed).
- **Live-run and verified with real data**: ran the backfill against the two real completed videos from earlier this session (both had raw, hours-old BytePlus URLs). Both migrated successfully — confirmed via a direct DB read afterward that `media_url` now points at `https://res.cloudinary.com/.../thunder/<task-id>.mp4` for both rows, `status` unchanged (`completed`). This was a free test (no new BytePlus generation cost) that exercises the exact same download-and-persist code path Part 1 uses on every future completion.

- Design system was **not** persisted to a `design-system/` folder — still small enough to track by reading the actual CSS/components.
- Dashboard mock lifecycle intentionally has a ~20% random failure rate so the error+retry UI path is actually exercised during manual testing, not just theoretical.
- Design direction for the canvas came from `ui-ux-pro-max` domain queries (style, ux) rather than `--design-system`, since no existing pattern in its database covers infinite node canvases — extended the already-established monochrome system (dark dotted background, `bg-card`/`border-border` node shells, low-opacity white edges) rather than introducing a new visual language for just this surface.
- Generate button and the ratio picker stayed inside `ChatRail` rather than moving onto the canvas/node itself — keeps the interaction model identical to Step 3's, and the instructions only specified where the *conversation* lives (the rail), not where the generate action triggers from.
- **Gemma API quirks discovered by live testing, not assumed from memory or a stale doc snapshot**:
  - `generationConfig.responseMimeType` / `responseSchema` (Gemini's constrained-JSON-output feature) return an instant HTTP 500 ("Internal error") on this model — not supported, despite being documented for Gemini-branded models. Worked around by requesting raw JSON via the system prompt instead and parsing leniently (strip markdown fences if present).
  - This model has **mandatory "thinking"** (extended reasoning) that runs by default and was adding 15–65+ seconds of latency per turn for zero benefit on a short-form classification/rewrite task like this. Fixed by setting `generationConfig.thinkingConfig.thinkingLevel: "minimal"` (confirmed via the live docs page in-browser — the correct enum value is `"minimal"`, not `"low"`, which 400s with "Thinking level is not supported for this model"). Brought latency down to ~1–3s per turn.
  - Response `parts[]` always includes the reasoning as separate `{"thought": true}` entries *before* the real answer, even with thinking minimized (sometimes an empty thought part). Must take the **last** part without `thought: true`, not `parts[0]` — reading `parts[0]` silently grabs the reasoning trace instead of the answer.
  - Free tier shows real flakiness under rapid repeated calls (occasional timeouts/500s that clear on a plain retry) — expected for a newly-released free-tier model, not a bug in the route. The retry-once contract absorbs most of this; a couple of manual test calls still needed a second manual retry beyond that during testing.
